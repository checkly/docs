# Page types

Pick one type per page, read two of its examples, then write. The examples were chosen because they
follow the current rules: sentence-case headings named for what the reader does, facts that were
checked recently, and no filler. Many older pages do not, so do not copy a page just because it is
nearby.

## Feature overview

The landing page of a product area, for example `resolve/traces/overview`. It answers: what is
this, what do I get, how does it work in two or three paragraphs, and where do I start.

- Open with one or two plain sentences: what the feature does for the reader. No "What is X?"
  heading.
- A `<Frame>` screenshot of the feature with real data.
- Short sections on how it works and on limits or plan availability, then links to the task
  pages. Cards only here, and only for navigation (`AGENTS.md`).
- Under about 800 words. Details belong on the task and reference pages.

Examples: `resolve/automatic-check-repair.mdx`, `communicate/status-pages/overview.mdx`.

## Task (how-to)

One job, done in the UI, the CLI or both: "Create a role", "Cancel a test session".

- First paragraph: the result and when you need it. A `Prerequisites` accordion only when the reader
  needs access, a plan or a version first.
- `##` headings are the tasks, written as imperatives ("Create a role"), never "Step N:".
- Numbered steps with the exact UI labels in bold. Say what the reader sees after the last step.
- Show the Monitoring as Code variant next to the UI variant when both exist.

Examples: `admin/team-management/custom-roles.mdx`, `detect/synthetic-monitoring/agentic-checks/migrate.mdx`,
`concepts/cancellation.mdx`.

## Setup per platform or vendor

One page per language, framework or third-party service, all with the same shape, for example
the trace export pages or SDK setup pages.

- Put the shared intro and outro in `snippets/` and import them, so the variants cannot drift.
- Numbered steps: get the value from the other system, paste it into Checkly (or the reverse),
  confirm the data arrives. Name the exact screen in the other product.
- A table for headers, environment variables or settings.
- Link the vendor's own docs for anything that is theirs to explain.
- Every sample ran against a real account with the package version recorded in `facts.md`.

Example: `integrations/observability/traces/dash0.mdx` with
`snippets/otlp-vendor-intro.mdx` and `snippets/otlp-vendor-outro.mdx`. The older pages in
`resolve/traces/instrumentation/` have the right scope but use "Step N:" headings and
"This guide will help you" filler; do not copy those parts.

## Reference

Every option of one thing: environment variables, construct properties, CLI flags, settings.

- A table or a definition list, one row per option: name in code format, default, allowed values,
  the version that added it, one or two sentences of effect.
- Complete. A reference that lists 9 of 10 options is wrong.
- No tutorials; link to the task pages.

Examples: `platform/private-locations/agent-configuration.mdx`, `constructs/dns-monitor.mdx`,
`cli/checkly-login.mdx`.

## Concept

How something works and why, when the reader needs a model before the tasks make sense:
scheduling, retries, grouping, data retention.

- Explain the mechanism with a concrete example. A diagram only when the idea is spatial or a
  sequence (`AGENTS.md` lists Mermaid).
- End with links to the tasks that use the concept.

Example: `concepts/environments.mdx`.

## Troubleshooting

Symptoms the reader sees, each with cause and fix.

- `##` headings group by area; each problem starts with the exact symptom (error message in code
  format, or the UI state).
- Cause in one sentence, fix as steps. Only problems that really happen, proven by reproduction or
  by support tickets.

Example: `ai/mcp-server/troubleshooting.mdx`.

## Changelog entry

Entries under `changelog/` and the private location agent change log follow the entries above them
on the same page: version, date, one line per change, link to the docs page that explains it.

## Not hand-written

- `api-reference/`: generated from `api-reference/openapi.json` by `update-api-spec.sh`.
- Runtime package lists: generated by the `update-runtime-spec` workflow.
- `guides/`: use the `guide-authoring` skill.
