## What Checkly stores

Checkly stores errors and messages. It skips every other kind of data an SDK sends, such as transactions, sessions, replays, logs and attachments, without failing the request.

## Data scrubbing

Checkly removes common secrets when an error arrives, before it stores, groups or symbolicates anything. Removed values are replaced with `[Filtered]`.

| Data | What Checkly does |
|---|---|
| IP addresses of the user and the request, including headers such as `X-Forwarded-For` | Removes them |
| `Authorization`, `Cookie`, `Set-Cookie`, API key and token headers | Replaces the value |
| Cookie values and request bodies | Replaces them, always |
| Values under names that contain `password`, `secret`, `token`, `apikey`, `auth`, `session`, `jwt` and similar, also in URLs | Replaces the value |
| Card numbers in messages, exceptions, tags, extra data and breadcrumbs | Replaces them |
| Error messages, tags, user ID, email and username | Keeps them as sent, except card numbers |

Checkly receives user data only when your SDK sends it. To remove more before it leaves your application, use `beforeSend` in the SDK.

## Retention

Checkly keeps each error for 30 days. After that, its stack trace, breadcrumbs and context are gone, and the error group keeps its status, assignee, counts and first and last seen dates.

## Limits

| Limit | Value |
|---|---|
| Errors per DSN | About 500 per second, and about 8 MiB per second |
| Request body | 16 MiB, compressed and uncompressed |
| JSON in one request | 2 MiB |
| Items per envelope | 100 |
| Compression | None, `gzip` or `br` |
| `environment` | 64 characters. Longer values are cut. |
| `release` | 200 characters. Longer values are cut. |
| Tag value | 200 characters. Longer values are cut. |
| Error timestamp | Up to 30 days in the past and 5 minutes in the future; otherwise Checkly uses the time it received the error |

## Ingest responses

The Sentry SDKs handle these responses for you. They help when you send errors yourself or through a [tunnel](/detect/errors/send-errors#send-through-your-own-domain).

| Status | Body | Meaning |
|---|---|---|
| `202` | `{"accepted":true,…}` | Checkly accepted the request. |
| `400` | `{"error":"malformed envelope"}` | The envelope could not be read. |
| `401` | `{"error":"invalid sentry_key"}` | The key is wrong or revoked. |
| `403` | `{"error":"origin not allowed"}` | The request came from a website that is not in the project's [allowed websites](/detect/errors/send-errors#allow-only-your-websites). |
| `413` | `{"error":"payload too large"}` or `{"error":"too many envelope items"}` | The request is over a limit. |
| `415` | `{"error":"unsupported content encoding, use gzip or br"}` | Use `gzip` or `br`. |
| `429` | `{"error":"rate limited"}` | Over the limit for this DSN, or Checkly is busy. Retry after the `Retry-After` seconds. |

Every `429` response carries a `Retry-After` header; over the limit for a DSN, it also carries `X-Sentry-Rate-Limits`. Errors refused with `429` are not stored. They show as [dropped data](#see-dropped-data).

## See dropped data

When Checkly refuses a request or does not store an error, a project's **Errors** tab shows **Data dropped in the last 24 hours**, with the count and the main reason.

For every project, open [**Account settings** > **Errors**](https://app.checklyhq.com/settings/account/errors), select **Usage** on the **Errors** page, or use the link on the notice. The **Dropped** column of the **Usage** table shows the errors Checkly did not store and the requests it refused, and the reasons, such as **DSN rate limit**, **Too large** or **Revoked DSN key**. A request refused before Checkly read it counts as a refused request, because Checkly cannot count the errors in it. A request your SDK sends again counts again.
