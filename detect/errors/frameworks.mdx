Each setup below is the smallest one that sends errors to Checkly with readable stack traces. Start with a [DSN](/detect/errors/send-errors#get-a-dsn). Tracing, replay and profiling options from Sentry's guides are not needed: Checkly [stores only errors and messages](/detect/errors/data-and-limits#what-checkly-stores).

## Next.js

Works with the App Router of Next.js 16.4 or later and `@sentry/nextjs` 11.14 or later, on Node.js 24.20 or later.

```bash Terminal
npm install @sentry/nextjs
npm install --save-dev @sentry/cli
```

Initialize the SDK for the browser and for the server, and report server errors with `onRequestError`:

```ts instrumentation-client.ts
import * as Sentry from '@sentry/nextjs'

Sentry.init({
  dsn: '<your-dsn>',
  environment: 'production',
})
```

```ts instrumentation.ts
import * as Sentry from '@sentry/nextjs'

export async function register() {
  if (process.env.NEXT_RUNTIME === 'nodejs') {
    Sentry.init({
      dsn: '<your-dsn>',
      environment: 'production',
    })
  }
}

export const onRequestError = Sentry.captureRequestError
```

Without `onRequestError`, errors in route handlers and server components are not sent. This setup starts the server SDK only when `NEXT_RUNTIME` is `nodejs`. You do not need `global-error.tsx` to capture errors, or `onRouterTransitionStart`, which only adds tracing.

For readable stack traces, let `withSentryConfig` set the release and the debug IDs, and upload the source maps with `sentry-cli` after the build. Import `withSentryConfig` from `@sentry/nextjs/config`:

```ts next.config.ts
import type { NextConfig } from 'next'
import { withSentryConfig } from '@sentry/nextjs/config'

const nextConfig: NextConfig = {
  productionBrowserSourceMaps: true,
}

export default withSentryConfig(nextConfig, {
  release: { name: 'storefront@2026.9.3' },
  sourcemaps: { disable: 'disable-upload' },
})
```

```bash Terminal
npx next build
npx sentry-cli sourcemaps upload --release storefront@2026.9.3 .next/static/chunks
npx sentry-cli sourcemaps upload --release storefront@2026.9.3 .next/server
find .next/static -name '*.map' -delete
```

Set the [`sentry-cli` variables](/detect/errors/source-maps#configure-sentry-cli) in the environment of the build. Delete the browser source maps before you deploy: `next start` serves them to anyone otherwise.

<Warning>
Do not let `withSentryConfig` upload Turbopack builds itself. It changes the built files after the source maps were written, so every frame resolves one line off. With `npx next build --webpack`, its own upload resolves browser errors, but route handler frames point at Sentry's wrapper module. The default Turbopack build with the `sentry-cli` steps above gives readable frames for both.
</Warning>

## React

Works with React 19.3 or later, Vite 8.3 or later, and `@sentry/react` and `@sentry/vite-plugin` 11.14 or later.

```bash Terminal
npm install @sentry/react
npm install --save-dev @sentry/vite-plugin @sentry/cli
```

Initialize the SDK before you render, and wrap the parts of your app that should show a fallback in `Sentry.ErrorBoundary`:

```tsx src/main.tsx
import * as Sentry from '@sentry/react'
import { createRoot } from 'react-dom/client'
import App from './App.tsx'

Sentry.init({
  dsn: '<your-dsn>',
  environment: 'production',
})

createRoot(document.getElementById('root')!).render(
  <Sentry.ErrorBoundary fallback={<p>Something went wrong.</p>}>
    <App />
  </Sentry.ErrorBoundary>,
)
```

An error that `Sentry.ErrorBoundary` catches arrives once, as handled. An error outside a boundary still arrives, as unhandled. If you also pass `Sentry.reactErrorHandler()` to `onCaughtError` of `createRoot`, errors the boundary catches arrive as unhandled instead.

For readable stack traces, let the Vite plugin inject debug IDs and the release, and upload the source maps with `sentry-cli` after the build:

```ts vite.config.ts
import react from '@vitejs/plugin-react'
import { sentryVitePlugin } from '@sentry/vite-plugin'
import { defineConfig } from 'vite'

export default defineConfig({
  build: { sourcemap: 'hidden' },
  plugins: [
    react(),
    sentryVitePlugin({
      release: { name: 'storefront@2026.9.3' },
      sourcemaps: { disable: 'disable-upload' },
    }),
  ],
})
```

```bash Terminal
npx vite build
npx sentry-cli sourcemaps upload --release storefront@2026.9.3 ./dist
rm dist/assets/*.map
```

Set the [`sentry-cli` variables](/detect/errors/source-maps#configure-sentry-cli) in the environment of the build.

<Warning>
Do not let `@sentry/vite-plugin` upload Vite builds itself. It changes the uploaded copy of the bundle, so every frame resolves one line off and points at the wrong file.
</Warning>

## Express

Works with Express 5.3 or later and `@sentry/node` 11.14 or later, on Node.js 24.20 or later.

```bash Terminal
npm install @sentry/node
```

```js instrument.mjs
import * as Sentry from '@sentry/node'

Sentry.init({
  dsn: '<your-dsn>',
  release: 'api@2026.9.3',
  environment: 'production',
})
```

Load it before your app:

```bash Terminal
node --import ./instrument.mjs app.mjs
```

Errors thrown in route handlers, sync or async, arrive as unhandled errors with the route, such as `GET /cart`, and a stack trace that points at your file and line. You do not need `Sentry.setupExpressErrorHandler(app)`; it is deprecated and does no harm. By default, only errors that end in a status of 500 or higher are sent. A crash at startup arrives too.

## Django

Works with Django 6.1 or later and `sentry-sdk` 2.75 or later, on Python 3.15 or later.

```bash Terminal
pip install sentry-sdk
```

Initialize the SDK at the top of `settings.py`. The Django integration turns itself on:

```python settings.py
import sentry_sdk

sentry_sdk.init(
    dsn="<your-dsn>",
    release="api@2026.9.3",
    environment="production",
)
```

Unhandled exceptions in views arrive with the view's file and line, under `runserver` and under gunicorn. To count [affected users](/detect/errors/send-errors#count-affected-users), add `send_default_pii=True`; the SDK then sends the logged-in user's ID, email and username.

`logger.error()` calls arrive as errors without a stack trace. `logger.warning()` and `logger.info()` are not sent as errors; they show as breadcrumbs of the next error.

## Laravel

Works with Laravel 13.43 or later and `sentry/sentry-laravel` 4.30 or later, on PHP 8.5 or later.

```bash Terminal
composer require sentry/sentry-laravel
```

Add the DSN, the release and the environment to `.env`:

```dotenv .env
SENTRY_LARAVEL_DSN=<your-dsn>
SENTRY_RELEASE=api@2026.9.3
SENTRY_ENVIRONMENT=production
```

Without `SENTRY_ENVIRONMENT`, the SDK uses `APP_ENV`. Then let the SDK report exceptions, in `bootstrap/app.php`:

```php bootstrap/app.php
<?php

use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;
use Sentry\Laravel\Integration;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware): void {
        //
    })
    ->withExceptions(function (Exceptions $exceptions): void {
        Integration::handles($exceptions);
    })->create();
```

Without `Integration::handles`, unhandled exceptions are not sent. With it, unhandled exceptions in routes arrive with the route file and line, and `report($e)` and `\Sentry\captureException($e)` arrive as handled. You do not need `php artisan sentry:publish`. To check the setup, run `php artisan sentry:test`: it prints `Test event sent with ID: …`, and the error arrives in Checkly.

`Log::error()` is not sent by default. If you add the `sentry` channel to `LOG_STACK`, for example `LOG_STACK=single,sentry`, log errors arrive without a stack trace, but every exception is then also reported a second time.

## Ruby on Rails

Works with Rails 8.1 or later and `sentry-ruby` and `sentry-rails` 7.3 or later, on Ruby 4.0 or later.

```bash Terminal
bundle add sentry-ruby sentry-rails
```

```ruby config/initializers/sentry.rb
Sentry.init do |config|
  config.dsn = '<your-dsn>'
  config.release = 'api@2026.9.3'
  config.environment = 'production'
end
```

Unhandled exceptions in controller actions and in Active Job jobs arrive with the file and line. `Sentry.capture_exception(e)` arrives as handled. You do not need `bin/rails generate sentry` or `config.breadcrumbs_logger`; `breadcrumbs_logger` only adds breadcrumbs.

`Rails.error.report(e)` is not sent unless you add `config.rails.register_error_subscriber = true`; then it arrives as handled. `Rails.logger.error` is not sent.

## Spring Boot

Works with Spring Boot 4.1 or later and `io.sentry:sentry-spring-boot-4-starter` 8.65 or later, on Java 25 or later.

```xml pom.xml
<dependency>
  <groupId>io.sentry</groupId>
  <artifactId>sentry-spring-boot-4-starter</artifactId>
  <version>8.65.0</version>
</dependency>
```

```properties application.properties
sentry.dsn=<your-dsn>
sentry.release=api@2026.9.3
sentry.environment=production
```

Unhandled exceptions in controllers arrive with the class and line, and the cause of a chained exception shows on the error group. `Sentry.captureException(e)` arrives as handled. You do not need `sentry.in-app-includes`: the starter marks the package of your `@SpringBootApplication` class as your code. The Sentry Maven and Gradle plugins are not needed either: frames show the file and line without them, and Checkly does not show the source bundles they upload.

To send `log.error("…", e)` calls as errors, add `io.sentry:sentry-logback` at the same version as the starter. Tomcat then also logs the root cause of a chained exception, so a second error arrives, in a separate error group, for the root cause. Drop it in a `BeforeSendCallback` bean:

```java SentryConfig.java
import io.sentry.SentryOptions;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class SentryConfig {
  @Bean
  public SentryOptions.BeforeSendCallback dropTomcatRootCauseLog() {
    return (event, hint) -> {
      String logger = event.getLogger();
      return logger != null && logger.startsWith("org.apache.catalina.core.ContainerBase.") ? null : event;
    };
  }
}
```

## ASP.NET Core

Works with .NET 11 or later and `Sentry.AspNetCore` 7.0 or later.

```bash Terminal
dotnet add package Sentry.AspNetCore
```

```csharp Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.WebHost.UseSentry(o =>
{
    o.Dsn = "<your-dsn>";
    o.Release = "api@2026.9.3";
    o.Environment = "production";
});

var app = builder.Build();

// Map your endpoints here.

app.Run();
```

Unhandled exceptions in endpoints arrive as unhandled, and `SentrySdk.CaptureException(e)` as handled. `ILogger.LogError()` creates an error; `LogWarning()` does not.

The SDK reads the file and line from the `.pdb` file at runtime, so deploy it next to the DLL, as `dotnet publish -c Release` does, or build with `-p:DebugType=embedded`. Without it, frames show only the function name. You do not need to upload symbols or sources: Checkly does not use them for .NET, and .NET stack traces show no source lines.
