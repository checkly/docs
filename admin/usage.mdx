Synthetic checks, such as API, Browser and Multistep checks and Playwright Check Suites, use check runs from your plan. Uptime monitors don't use check runs: they're billed by the number of monitors. See [pricing](https://www.checklyhq.com/pricing/) for what your plan includes.

## What counts as a check run

Each run of a check uses check runs, wherever it starts: scheduled runs, runs you start with **Schedule now**, test runs from the check editor, and test sessions from the CLI, such as `npx checkly test` and `npx checkly trigger`. On top of that:

- **Locations:** with parallel scheduling, each location counts. A check that runs from three locations in parallel uses three check runs each time it's scheduled.
- **Retries:** each retry is another check run. A flaky check that often retries uses noticeably more.
- **Multistep checks:** each HTTP request the check makes counts as one API check run, with at least one per run.
- **Playwright Check Suites:** each started 30 seconds of run time counts as one Browser check run.

For example, an API check that runs every hour from two locations in parallel uses 48 check runs a day. Each retry adds one more.

To use fewer check runs, lower the frequency of checks that don't need it, run from fewer locations, or use round-robin instead of [parallel scheduling](/concepts/scheduling), and fix flaky checks so they retry less.

## Estimating your monthly check runs

To estimate how many check runs a check uses in a month, multiply its runs per day by the days in the month and by the locations each run uses.

- **Runs per day:** divide 1,440, the minutes in a day, by the check's frequency in minutes. A check that runs every 5 minutes runs 288 times a day.
- **Locations per run:** with parallel scheduling, the number of locations you selected. With round-robin scheduling, it's 1, however many locations you select: each run uses one location, and the next run uses the next one.
- **Groups:** if the check is in a [group](/platform/groups) that sets locations or a scheduling strategy, use the group's settings.

Then adjust for the check type and for retries:

- **Multistep checks:** multiply by the number of HTTP requests the check makes in a run.
- **Playwright Check Suites:** multiply by the number of started 30-second blocks a run takes. A suite that runs for 70 seconds uses 3 Browser check runs each time.
- **Retries:** retries only happen when a run fails. Each retry adds one check run, so a check with 2 retries uses up to 3 check runs for a run that keeps failing. With parallel scheduling, count this for each location that fails.

Count only checks that are activated: deactivated checks don't run. Add up your checks separately for Browser and Playwright check runs, and for API and Multistep check runs, because your plan includes each separately. Runs you start yourself, such as test runs, **Schedule now** and CLI test sessions, come on top.

Examples for a 30-day month (a 31-day month adds about 3%):

| Check | Check runs per month |
|---|---|
| Every minute, 1 location | 1,440 × 30 × 1 = 43,200 |
| Every 5 minutes, 3 locations in parallel | 288 × 30 × 3 = 25,920 |
| Every 5 minutes, 3 locations round-robin | 288 × 30 × 1 = 8,640 |
| Every hour, 2 locations in parallel | 24 × 30 × 2 = 1,440 |
| Playwright Check Suite of 70 seconds, every 10 minutes, 1 location | 144 × 30 × 3 = 12,960 |

Compare your total with the check runs your plan includes, listed on the [pricing page](https://www.checklyhq.com/pricing/). Adding check runs to your plan in advance costs less per run than paying overage for them: see [Adding capacity](/admin/billing#adding-capacity). Uptime monitors don't count toward this total: see [Uptime monitors](#uptime-monitors).

## Uptime monitors

URL, TCP, DNS, ICMP, SSL, traceroute and gRPC monitors are billed by how many monitors you have, not by how often they run. Their runs don't use check runs.

## Seeing your usage

Select [**Billing & usage**](https://app.checklyhq.com/settings/account/billing) in the left sidebar. Every built-in role can open this page.

- The **Plan** card shows when the current period ends: **Free check runs are refreshed on** on the Hobby plan, **Free trial ends on** during a trial, and **Next billing period starts** on paid plans.
- The **Usage** card shows what the whole account has used in the current period against what your plan includes, for example `7 / 1,000`. Under **Synthetic Checks**, your check runs have two rows: Browser and Playwright check runs, and Multistep and API check runs. The **Playwright check runs (1 run every 30s)** row shows how many of the Browser and Playwright check runs came from Playwright Check Suites. The other rows show how many uptime monitors, status pages, users and other resources you have, against your plan's limits.

The figures can take a few minutes to catch up after checks run, and up to about 15 minutes on the Starter and Team plans. The page shows only the current period: it has no daily graph, no breakdown per check and no past periods. To work out how many check runs your checks use, see [What counts as a check run](#what-counts-as-a-check-run).

The [Usage API](/api-reference/usage/overview) and [`checkly account usage`](/cli/checkly-account) report usage per day for accounts with contract usage terms, which only Enterprise contracts have. For other accounts, they return no credits or run counts.

### Enterprise plans

On an Enterprise plan, the page has no **Usage** card. Owners, Admins and custom roles with the [**View usage**](/admin/team-management/permissions#usage) permission see a **Usage** tab next to **Plan & invoices** instead. It shows usage against your contract's credit budget for the period you pick (**7d**, **30d**, **Contract to date** or a custom range), credits per day, week or month under **Where credits went**, and a **Usage breakdown** per check type. Other roles don't see the tab.

## Usage emails

On Starter and Team plans, users who can manage billing (Owners and Admins by default) get an email when the account has used more than 90% of its included API or Browser check runs, and another one when it goes over and starts incurring overages. API and Browser check runs each get their own emails.

On the Hobby plan, checks stop running when the included check runs are used up. All members get an email at 80% and at 100% of the included check runs.
