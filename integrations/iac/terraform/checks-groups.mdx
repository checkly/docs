Checks make up the most important unit of your Checkly monitoring setup. Groups help you split them up according to your needs and keep complexity down.

## Checks

[Browser checks](/detect/synthetic-monitoring/browser-checks/overview), [API checks](/detect/synthetic-monitoring/api-checks/overview), [Heartbeat monitors](/detect/uptime-monitoring/heartbeat-monitors/overview) and [Multistep checks](/detect/synthetic-monitoring/multistep-checks/overview) share many arguments, configuration-wise, 
but also have their own unique ones. The type of your check is controlled using the `type` argument.

### Browser checks

For example, a Browser check can look as follows:

```terraform
resource "checkly_check" "e2e-login" {
  name                      = "Login flow"    // The name of the check
  type                      = "BROWSER"       // The type of the check
  activated                 = true            // Whether the check will start as active on creation
  frequency                 = 10              // The frequency of the check in minutes
  use_global_alert_settings = true            // Whether to use account level alert setting instead of the alert setting defined on this check
  run_parallel              = true            // Whether the check would run in a single location at time (round-robin) or all locations on each run

  locations = [                               // Which locations the check should run from (if not in a group)
    "us-west-1",
    "eu-central-1"
  ]

  retry_strategy {                          // The retry strategy used for failed runs
    type = "LINEAR"
  }            

  // The script the check should execute
  script = <<EOT
const { expect, test } = require('@playwright/test');

test('Login flow', async ({ page }) => {
  await page.goto('https://danube-web.shop/');
  await page.getByRole('button', { name: 'Log in' }).click();

  await page.getByPlaceholder('Email').type('user@email.com');
  await page.getByPlaceholder('Password').type('supersecure1');

  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByText(/Welcome back/)).toBeVisible();
});
EOT
}
```

For tidiness and ease of use, it is recommended to store scripts in separate files, instead of using the inline option:

```terraform
resource "checkly_check" "e2e-login" {
  name                      = "Login Flow"
  type                      = "BROWSER"
  activated                 = true
  should_fail               = false
  frequency                 = 1
  use_global_alert_settings = true

  locations = [
    "us-west-1",
    "eu-central-1"
  ]

  retry_strategy {
    type = "LINEAR"
  }

  script = file("${path.module}/scripts/login.spec.js") // Our script is contained in this file
}
```

> You can see all the configuration options for checks on the official Terraform registry [documentation page](https://registry.terraform.io/providers/checkly/checkly/latest/docs/resources/check#schema).

### API checks

On the other hand, an API check shares some part of the initial configuration, but is organized around the `request` argument instead of the `script` argument:

```terraform
resource "checkly_check" "get-books" {
  name                      = "GET /books"   // The name of the check
  type                      = "API"     // The type of the check
  activated                 = true      // Whether the check will start as active on creation
  should_fail               = false     // Whether the check's HTTP response's status is expected to be >399
  frequency                 = 1         // The frequency of the check in minutes
  use_global_alert_settings = true      // Whether to use account level alert setting instead of the alert setting defined on this check
  run_parallel              = true            // Whether the check would run in a single location at time (round-robin) or all locations on each run

  locations = [                         // Which locations the check should run from (if not in a group)
    "us-west-1",
    "eu-central-1"
  ]
  
  retry_strategy {                    // The retry strategy used for failed runs
    type = "LINEAR"
  }

  request {                             // All the settings for the check's HTTP request
    url              = "https://danube-web.shop/api/books"   // The request URL
    follow_redirects = true             // Whether the request should follow redirects
    skip_ssl         = false            // Whether to skip the SSL validation on the target server
    assertion {                         // One or more assertions to run against the HTTP response
      source     = "STATUS_CODE"        // What to assert against
      comparison = "EQUALS"             // How to assert
      target     = "200"                // Expected value
    }
  }
}
```

> You can see all the configuration options for checks on the official Terraform registry [documentation page](https://registry.terraform.io/providers/checkly/checkly/latest/docs/resources/check#schema).

### Heartbeat monitors

For example, a Heartbeat monitor can look as follows:

```terraform
resource "checkly_heartbeat_monitor" "send-weekly-digest-v-2" {
  name                      = "Send Weekly Digest"    // The name of the monitor
  activated                 = true                    // Whether the monitor will start as active on creation
  heartbeat {
    period                  = 7                       // The expected period of time between each ping. Between 30 seconds and 365 days.
    period_unit             = "days"                  // The unit of time for the period, the available options are `'seconds' | 'minutes' | 'hours' | 'days'`
    grace                   = 1                       // The grace period to wait for before sending an alert. Between 0 seconds and 365 days.
    grace_unit              = "days"                  // The unit of time for the grace period, the available options are `'seconds' | 'minutes' | 'hours' | 'days'`.
  }
  use_global_alert_settings = true                    // Whether to use account level alert setting instead of the alert setting defined on this check
}
```

Upon applying your Terraform configuration changes, you will be returned a read-only key value for the heartbeat ping token. The token is stored in your `tfstate` file.


### Multistep checks

As with Browser checks, when constructing a Multistep check it is possible to provide the script directly in-line, 
but the recommended approach is to store scripts in separate files.

> Multistep checks are only supported on runtime 2023.09 or later. See [Runtimes](/platform/runtimes/overview) for more details.

For example, a Multistep check can look as follows:
```terraform
 resource "checkly_check" "e2e-shopping" {
  name                      = "Shopping Flow"
  type                      = "MULTI_STEP"
  activated                 = true
  should_fail               = false
  frequency                 = 1
  use_global_alert_settings = true
  locations = [
    "us-west-1",
    "eu-central-1"
  ]

  script = file("${path.module}/scripts/shopping.js")
}
```


### TCP monitors

TCP monitors verify the availability and responsiveness of services running on specific ports, ensuring they are reachable and operating within acceptable response time thresholds.

Below is a sample configuration for a TCP monitor using Terraform:

```terraform
resource "checkly_tcp_monitor" "example-tcp-monitor-2" {
  name                   = "Example TCP monitor 2"
  activated              = true
  should_fail            = true
  frequency              = 1
  degraded_response_time = 4000
  max_response_time      = 5000

  locations = [
    "us-west-1",
    "ap-northeast-1",
    "ap-south-1",
  ]

  alert_settings {
    escalation_type = "RUN_BASED"

    run_based_escalation {
      failed_run_threshold = 1
    }

    reminders {
      amount = 1
    }
  }

  retry_strategy {
    type                 = "FIXED"
    base_backoff_seconds = 60
    max_duration_seconds = 600
    max_retries          = 3
    same_region          = false
  }

  request {
    hostname = "api.checklyhq.com"
    port     = 80
    data     = "hello"

    assertion {
      source     = "RESPONSE_DATA"
      property   = ""
      comparison = "CONTAINS"
      target     = "welcome"
    }

    assertion {
      source     = "RESPONSE_TIME"
      property   = ""
      comparison = "LESS_THAN"
      target     = "2000"
    }
  }
}
```

## Groups

Once you start having more than just a handful of checks, it makes sense to start looking into [groups](/platform/groups) to keep things tidy. Use the `checkly_check_group_v2` resource. A v2 group doesn't override any settings of its checks unless you ask it to, so it can be as simple as a name:

```terraform
resource "checkly_check_group_v2" "key-shop-flows" {
  name = "Key Shop Flows"
}
```

To have the group override a setting for all of its checks, add the matching `enforce_*` block and set `enabled = true`. The available blocks are `enforce_locations`, `enforce_retry_strategy`, `enforce_scheduling_strategy` and `enforce_alert_settings`:

```terraform
resource "checkly_check_group_v2" "key-shop-flows" {
  name        = "Key Shop Flows"
  activated   = true
  muted       = false
  concurrency = 3 // How many checks to run at once when triggering the group using CI/CD triggers

  // All checks in this group run from these locations, regardless of their own settings
  enforce_locations {
    enabled   = true
    locations = ["eu-west-1", "eu-central-1"]
  }
}
```

The older `checkly_check_group` resource still works, but it always applies group-level defaults to its checks. See [migrating to `checkly_check_group_v2`](#migrating-to-checkly_check_group_v2) below.

You can see all the configuration options for groups, as well as more examples, on the Terraform registry documentation pages for [`checkly_check_group_v2`](https://registry.terraform.io/providers/checkly/checkly/latest/docs/resources/check_group_v2) and [`checkly_check_group`](https://registry.terraform.io/providers/checkly/checkly/latest/docs/resources/check_group).

### Adding checks to groups

To add a check to a group, link it to that group by setting the `group_id` argument to the group's resource ID. For example, to link the API check and the group from this article:

```terraform
resource "checkly_check" "get-books" {
  name                      = "GET /books"
  type                      = "API"
  activated                 = true
  should_fail               = false
  frequency                 = 1
  use_global_alert_settings = true

  locations = [
    "us-west-1",
    "eu-central-1"
  ]

  // This makes the check part of the group
  group_id = checkly_check_group_v2.key-shop-flows.id

  retry_strategy {
    type = "LINEAR"
  }

  request {
    url              = "https://danube-web.shop/api/books"
    follow_redirects = true
    skip_ssl         = false
    assertion {
      source     = "STATUS_CODE"
      comparison = "EQUALS"
      target     = "200"
    }
  }
}
```

> With a `checkly_check_group_v2` group, a check keeps its own settings unless the group enables the matching `enforce_*` block. With the older `checkly_check_group`, locations and alert channel subscriptions defined at group level always override the ones defined at check level.

### Migrating to `checkly_check_group_v2`

<Warning>
Don't migrate by only changing the resource type from `checkly_check_group` to `checkly_check_group_v2`. Terraform then deletes the old group and creates a new one, and **deleting a group deletes every check in it**. Terraform recreates the checks afterwards, but with new IDs and without their result history.
</Warning>

Move the existing group to the new resource type instead, so the group and its checks stay in place:

1. Note the group's ID:

   ```bash
   terraform state show checkly_check_group.key-shop-flows
   ```

2. In your configuration, replace the `checkly_check_group` resource with a `checkly_check_group_v2` resource with the same resource name (`key-shop-flows` here). To keep the old behavior, add `enforce_*` blocks for the settings the old group set, such as locations, retry strategy, scheduling strategy and alert settings. Update every reference, for example `group_id = checkly_check_group_v2.key-shop-flows.id`.

3. Remove the old resource from the Terraform state. This doesn't change anything in Checkly:

   ```bash
   terraform state rm checkly_check_group.key-shop-flows
   ```

4. Import the existing group as the new resource, using the ID from step 1:

   ```bash
   terraform import checkly_check_group_v2.key-shop-flows <group-id>
   ```

5. Run `terraform plan`. It must not destroy or replace any resource. An in-place update of the group is expected; check that it only turns off `enforce_*` settings you meant to drop. Then run `terraform apply`.

### Deleting a group

<Warning>
Deleting a group also deletes all checks in it. To keep the checks, first remove `group_id` from them and apply that change. Then remove the group from your configuration and apply again.
</Warning>
