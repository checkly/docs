An Error Group collects every Error with the same cause, so a bug that fails a thousand times is one entry to triage. You resolve, ignore, assign, merge and split Error Groups on the **Errors** page, through the [API](/resolve/errors/api) or with an AI agent through the [MCP server](/resolve/errors/api#mcp-tools).

## How Errors are grouped

Checkly picks the grouping key for each Error in this order:

1. The `fingerprint` your SDK sends, if it is set. Use `{{ default }}` in it to extend the default key instead of replacing it.
2. The exception type and the top frames of your own code in the stack trace.
3. The Error message, with variable parts such as IDs and numbers removed.

Content hashes in file names, build directories and dependency versions are not part of the key, so a new build of the same code joins the same Error Group. Errors in two projects are always in two Error Groups.

When you [upload source maps or debug files](/resolve/errors/source-maps), an Error whose resolved stack matches an existing Error Group joins it, even if the minified stack differs.

To group Errors your own way, set the fingerprint in the SDK, for example in JavaScript:

{/* [UNVERIFIED] Run this fingerprint sample against production. */}

```js app.js
Sentry.withScope((scope) => {
  scope.setFingerprint(['{{ default }}', 'checkout'])
  Sentry.captureException(error)
})
```

## Status and regressions

An Error Group is **Unresolved**, **Resolved** or **Ignored**.

- **Resolve** when you have shipped a fix. If a new Error arrives later, the Error Group reopens as **Unresolved** and shows the **Regressed** badge.
- **Ignore** an Error Group you do not plan to fix. New Errors do not reopen it. Select **Stop ignoring** to bring it back.
- **Reopen** a resolved Error Group by hand.

Select several Error Groups on the **Errors** page to change their status at once.

## Assign an Error Group

Assign an Error Group to a member of your account. Filter the list by **Assignee** to see what is yours (**Me**), someone else's (**Not me**) or nobody's (**Unassigned**).

## Merge Error Groups

When two Error Groups have the same cause, select them on the **Errors** page and select **Merge**. Checkly moves the grouping keys, Errors, history and counts into the Error Group you choose. The merged Error Groups are kept, and their links open the Error Group they were merged into. You can undo a merge.

## Split an Error Group

An Error Group can hold several grouping keys, for example after a merge. Its page lists them under **Grouping**. Select **Split out** on a key to move it, with its past and future Errors, into a new Error Group.

You cannot split out:

- an Error Group's only key;
- a key Checkly computed from the stack trace after applying your source maps or debug files, because that key is what the Error Group is;
- the last key that was not computed that way.

## Find Error Groups

Filter the **Errors** page by project, **Environment**, **Status**, **Assignee** and **Unhandled**, or search by title. Sort by number of Errors, last seen or age, over the last hour up to the last 30 days. The **Users** column counts affected users when your SDK [sends a user ID](/resolve/errors/send-errors#count-affected-users).

## Hand an Error Group to an AI agent

On an Error Group's page, **Copy for agent** copies a prompt with the Error, its stack trace and breadcrumbs for your coding agent. It leaves out contexts, tags, user data and URL query strings.

## Permissions

| Action | Permission |
|---|---|
| View Error Groups, Errors, stack traces and breadcrumbs | `error-groups:read` (every built-in role) |
| Resolve, ignore, reopen, assign, merge and split | `error-groups:update` (Read & Write, Admin and Owner) |

See [Permissions](/admin/team-management/permissions).
