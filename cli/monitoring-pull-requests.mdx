Use a pull request to bring a UI-created resource into code or keep an existing code-managed resource in sync. Review and test the changes, merge them, then deploy the project to Checkly.

<Accordion title="Before you begin">

  - You need access to edit the Checkly resource and use the account's GitHub integration. If the **Code** tab is missing, ask your account administrator to check your permissions.
  - Grant the Checkly GitHub App access to the repository, following the [GitHub integration setup](/integrations/ci-cd/github/deployments#set-up-github-deployment-hooks). You do not need to configure a deployment hook for this workflow.
  - For local review, use a Git checkout and the [CLI prerequisites](/cli/installation). Use a Node.js version supported by the installed `checkly` package. The checkout commands below use the [GitHub CLI](https://cli.github.com/manual/gh_pr_checkout); you can also use the checkout instructions on the GitHub PR page.
</Accordion>

## 1. Connect GitHub and choose the repository

Open the resource's **Export to code** dialog and select **Code**. If prompted, connect GitHub from Checkly and grant the App access to your repository.

For a UI-created resource, select **Choose a repository**. If the repository contains multiple Checkly configs, enter the folder containing the intended project. Checkly can add the resource to a project already deployed to this account, or generate a new `checkly.config.ts` when the selected folder has no project.

For a code-managed resource, Checkly uses its owning project's repository and source file. If several files could declare the resource, confirm the correct file. A resource that a project only **References** is not owned by that project and cannot be synced through it.

## 2. Export the resource or push its UI changes to code

- **UI-created resource:** click **Export to code** to open a PR with the generated construct and any required files. Checkly reserves the existing resource for the target project; monitoring continues. This temporary link keeps ownership pending and protects the resource from deletion by deployments that omit it.
- **Code-managed resource edited outside code:** save your UI changes, then click **Sync to code**. Checkly opens or updates a PR that writes those changes to its construct. If the dialog says **Already in Sync**, there is no change to send.

Open the PR from the dialog or the project's **Pull requests** view in **Projects**. This view tracks PRs created through Checkly and lets you filter by **Open**, **Merged**, or **Closed**. Review, close, reopen, and merge them on GitHub.

## 3. Check out the PR and install dependencies

From your local repository checkout, select the PR:

```bash Terminal
gh pr checkout
```

Open a terminal in the folder containing its `checkly.config.ts` or `checkly.config.js`. In a monorepo, use the package or workspace that owns that config.

Install the repository's dependencies with its package manager. For npm projects:

```bash Terminal
npm install
```

If that package does not already declare `checkly`, add it:

```bash Terminal
npm install --save-dev checkly
```

Keep the existing Checkly version when one is already declared. The export PR does not create `package.json` or update dependencies and lockfiles. If you need a package manifest, follow [CLI installation](/cli/installation), then commit the manifest and lockfile changes to the PR.

Use your repository's package manager throughout:

| Package manager | Add Checkly if missing | Run CLI commands |
| --- | --- | --- |
| npm | `npm install --save-dev checkly` | `npx checkly` |
| pnpm | `pnpm add --save-dev checkly` | `pnpm exec checkly` |
| Yarn | `yarn add --dev checkly` | `yarn checkly` |

The remaining examples use npm. Replace `npx checkly` with your package manager's command as needed.

## 4. Authenticate, review, and test

Select the Checkly account that owns the resource:

```bash Terminal
npx checkly login
npx checkly whoami
```

If you already authenticate through `CHECKLY_API_KEY` and `CHECKLY_ACCOUNT_ID`, run `whoami` to confirm the account. Follow [CLI authentication](/cli/authentication) for local or CI setup.

Review the generated files and keep the project's `logicalId` and the exported construct IDs. These identify the reserved resources. Ensure your config's file patterns load the exported constructs.

Configure any secrets required by the files in your local environment and deployment CI. Exported credentials can be blank or read from environment variables. Supply them before testing and deploying; deploying a blank value can overwrite the existing credential. See [environment variables](/cli/environment-variables).

Test the checks defined in the checked-out code:

```bash Terminal
npx checkly test
```

Resolve failures before merging. Testing does not deploy monitoring configuration or finalize an export reservation. For a PR containing only an alert channel or another non-check resource, testing may report no checks; review the construct and its deployment preview instead.

```bash Terminal
npx checkly deploy --preview
```

Review changes across the entire project, including deletions. A preview leaves ownership pending. See [`checkly test`](/cli/checkly-test) and [`checkly deploy`](/cli/checkly-deploy) for options.

## 5. Update, close, reopen, or merge the PR

- **Update code:** edit the PR branch, stage the intended files, commit, and push. Include dependency and lockfile changes, then rerun tests.
- **Update from the UI:** save the resource again and use **Update PR** or **Sync to code**, as offered by the dialog. Checkly updates the open PR for that resource. Review the whole diff afterward: syncing an already code-managed resource rebuilds the branch from the repository's default branch and can replace your branch edits. Updating a pending export preserves other branch files but rewrites the generated resource files.
- **Close without merging:** close the PR on GitHub. Before adoption, Checkly releases its pending reservation when it processes the close, unless another live PR still uses that reservation. The live resource remains. Closing a sync PR does not undo the UI edit.
- **Reopen:** reopen the PR on GitHub. Checkly tries to reserve the original identities again. If another import or project has taken them, resolve the conflict before exporting again. A merged PR cannot be reopened.
- **Merge:** merge the reviewed PR on GitHub. The merged files are ready for deployment; merging alone does not apply them to Checkly.

Deploy after merging. A real deploy from the PR branch can establish ownership before merge, and closing the PR afterward does not undo that ownership or any deployed changes.

## 6. Deploy the merged code

Switch to the branch the PR was merged into and pull its latest changes. From the folder containing the Checkly config, install dependencies again and deploy:

```bash Terminal
git pull --ff-only
npm install
npx checkly whoami
npx checkly deploy --preview
npx checkly deploy --output
```

Confirm that the preview includes the exported resources and the expected project changes before proceeding with deployment.

Alternatively, let your existing CI deploy the merged commit. It must load the correct config, install the declared dependencies, and have the same account credentials and required secrets. Use `npx checkly deploy --force` for an authorized CI deployment. Follow the [CI/CD setup guides](/integrations/ci-cd/overview).

A successful deployment that includes all exported resource declarations under their reserved IDs finalizes adoption automatically. You do not need `checkly import`, `checkly import apply`, or `checkly import commit` for the UI-to-PR flow. A failed deployment rolls adoption back; a preview or deployment that omits a required reserved declaration leaves it pending.

After adoption, the project updates the same resource IDs, preserving their existing history. Future deployments apply your code to those resources, including overwriting UI edits. Removing an owned resource from code deletes it on the next deploy unless you use [`--preserve-resources`](/cli/checkly-deploy#deleting-vs-detaching-removed-resources).

## 7. Confirm completion

In Checkly, confirm all three:

1. The project's deployment history shows **Succeeded** for the intended deployment. Use its commit information when available to confirm the merged revision.
2. The exported resource shows **Managed by** the intended project instead of **Importing into**. Its resource ID and existing history remain the same.
3. The tracked PR shows **Deployed**. A sync PR's **Merged · awaiting deploy** badge should clear after the deployment applies its code.

**Code managed** can also mean an import was explicitly committed without deploying. Confirm the deployment history as well. PR state updates can arrive after the GitHub action; refresh the view if needed.

## When you use manual CLI import instead

The dialog's **CLI** tab supplies an import command for a resource. This is a separate workflow: it generates files locally, and you create your own Git branch and PR. Follow [Importing resources from the UI](/cli/importing) for selection and code generation.

| Flow | What establishes the link | What finalizes ownership |
| --- | --- | --- |
| UI **Code** tab export PR | Checkly creates and applies the reservation. | A successful deploy containing all required reserved declarations; no import commands required. |
| Manual CLI import | `npx checkly import` generates a plan and code; `npx checkly import apply` creates pending links. | `npx checkly import commit`, including when you accept the interactive commit prompt. A normal deploy does not automatically commit a manual plan. |
| Sync an already owned resource | Its project already owns it. | Deploying applies the PR's configuration; no import commands required. |

The manual import command can offer to apply and commit immediately. If you defer those prompts, the separate commands are:

```bash Terminal
npx checkly import apply
```

Review the generated code before applying. Decline the commit prompt if you want to keep ownership pending while you test and review your PR. After merging the import code, finalize it in that project and deploy:

```bash Terminal
npx checkly import commit
npx checkly deploy --output
```

`import commit` is a Checkly ownership operation, separate from a Git commit. Before applying a manual plan, deploying its generated files creates duplicates. After applying, deployments can update the existing resources, but the pending import protects them from deletion until commitment. You can cancel an uncommitted plan with `npx checkly import cancel`; cancellation does not undo changes already deployed.

## Recover from actionable failures

| What you see | What to do |
| --- | --- |
| Repository missing or GitHub access denied | Confirm the App is connected to this Checkly account and granted access to that repository, then retry. |
| Multiple Checkly configs | Enter the folder containing the intended config, rather than exporting into another project. |
| Project not deployed, unreadable `logicalId`, or a different repository binding | Check the config and account. Use the manual import workflow in the intended project if Checkly cannot adopt it automatically. |
| No source file or several candidates | Confirm the file that declares the construct. For an existing code-managed resource, check the project's `repoUrl` and `logicalId`; correct and deploy the config if needed. If the declaration is dynamic or cannot be patched, edit its code directly and open a PR. Importing is for resources that are not already owned. |
| Unsupported export or sync | Use manual import for a UI-created resource if the CLI supports its type. For an already owned resource, update its construct directly. |
| Cannot load the project, missing secret, or test failure | Install dependencies in the owning package, supply the required secrets, check `whoami`, and fix the reported configuration or test error before merging. |
| Unsupported Node.js version during installation | Use a Node.js version allowed by the `checkly` package's `engines.node` field, then reinstall dependencies. |
| Reservation released, superseded, or **Needs attention** after reopening | Resolve the current owner or pending import, then export or import again. Do not deploy the stale export code until its identities are linked again. |
| GitHub error while opening the PR | Check GitHub and the tracked PR view first: the PR may already exist. Retry after fixing App access. An uncertain creation result keeps the reservation protected; cancel the specific uncommitted plan with `checkly import cancel` if abandoning it. |
| Merged but awaiting deployment, or ownership still pending | Deploy the merged code to the correct account and project. Check that file patterns load every exported construct. For a manual import, finish `checkly import commit`. |
| Deployment failed | Read the deployment error, correct it, preview, and retry. Confirm **Succeeded** and resource ownership afterward. |
